Delayed Payment

Nov 2026 • 9 min read • payments · scheduling · idempotency

Understanding the problem

A user wants to send Robux to another user, not now but at a time they choose: a gift that arrives on a birthday, or a creator payout scheduled for the end of the month. The system must hold onto that intent, possibly for weeks, then move the money exactly once at (or very close to) the chosen time. It sounds like a scheduler question, but it's really a money question: the interviewer is listening for how you prevent double payments and lost payments.

Functional requirements

Core (above the line):

  1. A user can schedule a transfer: sender, receiver, amount, and an execute time.

  2. A user can cancel a scheduled transfer before it runs.

  3. The transfer executes at the scheduled time, moving the Robux from sender to receiver.

  4. A user can see the status of their scheduled transfers.

Below the line (say these out loud, then leave them):

  • Recurring payments ("every month")

  • Currency conversion and fees

  • Fraud scoring before the payout

  • Notifications beyond a simple "your payment ran" event

Non-functional requirements

  1. Exactly-once effect. A payment must never run twice and never silently disappear. This beats everything else.

  2. Timeliness. Execute within a few seconds of the scheduled time. The execute time can be seconds away, so a once-a-minute cron isn't good enough.

  3. Handles spikes. Many payments land on the same instant: midnight, the 1st of the month, the end of a game event. Assume up to ~1M due in the same minute.

  4. Auditable. Every movement of money is traceable after the fact.

  5. Highly available for scheduling, but correctness wins over availability for execution: it's better to run a payment 30 seconds late than twice.

Numbers to state: about 5,000 new scheduled payments per second at peak, ~100M pending at any time, ~200 bytes each, so about 20 GB. This easily fits in a sharded SQL database.

Clarifying questions to ask early:

  • Does the sender need the money now or at execution time? I'll assume we hold it now, so the payment can't fail later for insufficient funds.

  • What if the receiver's account is banned or deleted by then? I'll assume we refund the sender.

  • Can the execute time be seconds away? (Assume yes.)

The set-up

Core entities

Start with the nouns. Say them out loud before drawing anything:

  • ScheduledPayment: who pays whom, how much, when, and its status.

  • Account / Balance: a user's Robux, split into available and held.

  • LedgerEntry: one immutable record per movement of money (hold, release, debit, credit). The ledger is the source of truth; balances are a convenient summary of it.

API

POST /payments
{ "to_user": "u_42", "amount": 500, "execute_at": "2026-12-01T00:00:00Z",
  "idempotency_key": "c1b9…" }
→ 201 { "payment_id": "pay_123", "status": "SCHEDULED" }

POST /payments/{payment_id}/cancel
→ 200 { "status": "CANCELLED" }      // 409 if it already started running

GET /payments/{payment_id}
→ 200 { "status": "COMPLETED", "executed_at": "…" }

GET /users/me/payments?status=SCHEDULED

Two things to point out:

  • The sender comes from the auth token, never from the request body. Otherwise anyone could spend anyone's Robux.

  • POST /payments takes an idempotency key. If the client times out and retries, the same key returns the same payment instead of creating a second one. Say this unprompted; it's the first signal that you think about money correctly.

High-level design

Build it one requirement at a time. Each step adds only what that requirement needs.

1. Users can schedule a transfer

A Payment Service behind an API gateway writes to a SQL database (Postgres or MySQL). SQL is the right default for money: you need transactions that touch several rows at once.

In one transaction:

  1. Check the sender's available balance covers the amount.

  2. Move the amount from available to held (UPDATE balances SET available = available - 500, held = held + 500 WHERE user_id = 'u_7' AND available >= 500). The available >= 500 condition makes the check and the update atomic.

  3. Insert the scheduled_payments row with status = SCHEDULED.

  4. Append a HOLD ledger entry.

If any step fails, everything rolls back. The idempotency key has a UNIQUE constraint, so a retried request hits the constraint and returns the existing payment.

2. Users can cancel

Cancel is one conditional update: UPDATE scheduled_payments SET status = 'CANCELLED' WHERE payment_id = ? AND status = 'SCHEDULED'. If it changes a row, release the hold (held → available) and append a RELEASE ledger entry, in the same transaction. If it changes zero rows, the payment already started, so return 409. The condition is what makes "cancel while it's running" safe.

3. The transfer executes on time

This is the interesting part. Two new pieces:

  • Scheduler workers find payments that are due and claim them.

  • Executor workers do the actual money movement.

Flow:

  1. The table has an index on (status, execute_at). Each scheduler worker owns some database shards and, about every second, claims a batch of due rows:

UPDATE scheduled_payments
SET status = 'PROCESSING', lease_owner = 'worker-17', lease_until = now() + interval '30 seconds'
WHERE payment_id IN (
  SELECT payment_id FROM scheduled_payments
  WHERE status = 'SCHEDULED' AND execute_at <= now()
  ORDER BY execute_at LIMIT 500
  FOR UPDATE SKIP LOCKED)
RETURNING payment_id;

SKIP LOCKED lets many workers claim from the same table without stepping on each other.

  1. Claimed payment IDs go onto a queue (Kafka or SQS), partitioned by sender.

  2. An executor takes a payment and, in one transaction: subtracts the amount from the sender's held, adds it to the receiver's available, writes DEBIT and CREDIT ledger entries, and sets status = COMPLETED, only if the row is still PROCESSING with this worker's lease.

  3. It publishes a payment.completed event for notifications.

4. Users can see status

Reads go straight to the payment row (GET /payments/{id}), served from a read replica. For the "my scheduled payments" list, an index on (from_user, status, execute_at).

Potential deep dives

1. How do you implement the delay?

This is the question interviewers push hardest on. Walk through the options out loud and say why you reject each one.

Bad solution: a cron job every minute. A job wakes up each minute, selects everything due, and processes it.

  • Challenges: up to 59 seconds late, which misses the "seconds away" requirement. At the peak minute it pulls ~1M rows in one burst. If the job crashes halfway, which payments ran?

Good solution: a delay queue. When a payment is scheduled, put a message on a queue with a delivery delay (SQS delay, RabbitMQ delayed exchange, Kafka plus a timer service).

  • Challenges: most delay queues have a maximum delay (SQS: 15 minutes), so far-future payments need re-queuing. Cancelling means finding and removing a message already in the queue, which queues are bad at; you'd check status at execution anyway. The queue becomes a second source of truth beside the database.

Great solution: the database is the schedule. Payments stay in SQL with an index on (status, execute_at). Scheduler workers, each owning a set of shards, poll every ~1 second with FOR UPDATE SKIP LOCKED and a lease, then hand claimed IDs to a queue for execution.

  • Any delay works, from 3 seconds to 3 months. Cancel is a single conditional update. There's one source of truth, and it already has transactions.

  • Polling every second per shard is cheap because the query is an index range scan over only the due rows.

  • Refinement for very tight latency: a timing wheel in Redis (sorted set keyed by execute time, score = timestamp) holding the next few minutes of payments, loaded from the database. Workers pop items whose score ≤ now. The database stays the source of truth; Redis is just a fast index of what's coming soon.

2. How do you guarantee a payment never runs twice?

Accept that delivery is at-least-once (workers crash, queues redeliver) and make execution idempotent, so a second attempt is a no-op.

Bad solution: check status, then update. SELECT status, and if it's PROCESSING, do the transfer. Two workers can both read PROCESSING and both pay. This is a race condition.

Good solution: a conditional update as the guard. The executor's transaction starts with UPDATE scheduled_payments SET status = 'COMPLETED' WHERE payment_id = ? AND status = 'PROCESSING' AND lease_owner = ?. If it changes 0 rows, someone else already did it: roll back and stop.

Great solution: the guard plus a ledger constraint. Also put a UNIQUE (payment_id, entry_type) constraint on the ledger. Even if a bug bypasses the status check, the database itself refuses a second DEBIT for the same payment. Then add a nightly reconciliation job that checks every user's balance equals the sum of their ledger entries, and alerts on any difference.

The crash question: "The executor crashes after debiting but before marking COMPLETED." Because debit, credit, ledger and status are in one database transaction, there is no "after debiting but before completing": either all of it committed or none of it did. If none did, the lease expires, a sweeper resets the row to SCHEDULED, and another worker retries.

3. A million payments due at the same minute

Bad: one scheduler process. It becomes the bottleneck and a single point of failure.

Good: shard the payments table by payment_id; run a scheduler worker per shard group; claim in batches of 500.

Great: the above, plus:

  • Executors autoscale on queue depth.

  • The queue is partitioned by sender, so one sender's payments run in order and never fight over the same balance row.

  • Hot receivers (a popular creator receiving thousands of payouts at once) are the real hot spot: credit them through a per-user append-only ledger and update the summary balance in batches, instead of locking one balance row thousands of times a second.

  • State the trade-off: at the peak, some payments may run a few seconds late. That's acceptable; double-paying isn't.

4. The receiver is banned when the payment runs

Mark the payment FAILED, then run a compensating step: release the sender's hold back to available and write a RELEASE ledger entry. Notify the sender. Never leave Robux stuck in held. A periodic job also finds payments stuck in PROCESSING past their lease and resolves them.

5. Payments that depend on each other

A common follow-up: payment B depends on payment A, and A is being retried. Options: partition the execution queue by sender so a sender's payments always run in order, or fail B fast with a clear error and let the user reschedule it. Name both and pick one, then explain why.

Final design

The payment service holds the funds and inserts the payment in one transaction. Scheduler workers claim due rows with a lease and queue them by sender; executors move the money and mark the payment complete in one transaction, guarded by status and lease. A sweeper returns expired leases to SCHEDULED, and a nightly reconciliation checks every balance against the ledger. The Redis timing wheel is optional, only for tighter latency.

What's expected at each level

Mid-level (IC2). A working design: SQL table with execute_at, some background worker that runs due payments, and a cancel endpoint. Should recognize that duplicate execution is a risk, even if the fix needs a nudge.

Senior (IC3–IC4). Drives the whole thing without prompting. Holds funds at scheduling time and explains why. Compares cron vs delay queue vs database polling and picks one with reasons. Makes execution idempotent with a conditional update and a ledger constraint, handles the crash-midway question with transactions, and has a concrete answer for the peak minute (sharding, SKIP LOCKED, autoscaling, partition by sender). Names real SQL and real keys.

Staff+ (IC5). All of the above, plus: a reconciliation and audit story, compensating actions for every failure path, multi-region (which region owns a user's balance), and operational concerns: what to monitor (payments overdue by more than N seconds, stuck in PROCESSING), how to roll out changes to the executor safely.
